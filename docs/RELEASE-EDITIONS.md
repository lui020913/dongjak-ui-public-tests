# 동작하는 안전지도 — 공개 버전·개발 빌드 정책 (2026-11-19)

사용자에게는 `9.0`, `9.1`처럼 두 자리의 버전 계열(major.minor)을 표시한다. minor는 0~9를 사용한다. 내부 package.json, lockfile, 릴리스 원장, 배포 검증은 3자리 SemVer와 Git commit SHA, Actions run ID를 유지한다. `9.0.0`과 `9.0`은 서로 다른 정식 출시가 아니라 내부 번호와 표시 이름이다.

| 상태 | 화면 표시 예 | 실제 의미 |
|---|---|---|
| 변경 중 | 9.0 · 개발 빌드 | 검증된 배포 마커 없음 |
| Preview | 9.0 Developer Beta 1 | 해당 후보 빌드의 검증용 배포 |
| 후보 변경 후 Preview | 9.0 Developer Beta 2 | 동일 목표 버전의 다음 개발 후보 |
| RC (선택) | 9.0 RC | 출시 후보로 명시적으로 지정한 검증 빌드 |
| Production | 9.0 | 동일 검증 소스의 운영 배포 확인 |

- Major: 지원 플랫폼·서비스 호환성·핵심 분석체계의 실질적인 구조 변화.
- Minor: 독립적인 사용자 기능, 데이터 신규 연동, 광범위한 사용자 흐름 추가.
- Patch: 기존 기능의 오류 수정, 정렬, 성능, 안정성 개선. 내부 세 번째 번호와 빌드 ID로 추적하며 공개 표시 계열은 유지한다.
- 9.9 이후 숫자를 늘리기 위해 인위적으로 Major를 발행하지 않는다. 기능 단위를 묶어 다음 실제 세대 변경을 결정한다.
- 베타 번호는 동일 목표 버전의 변경된 후보가 Preview로 만들어질 때만 증가한다. 동일 소스 테스트 재실행에는 Actions run/attempt ID를 사용한다. Preview 실패는 정식 릴리스가 아니다.
- 이전 source marker가 Production인 경우만 운영 상태를 확인한 것으로 본다. release-source.json 의 application_version 일치와 release_status 검증 없이는 정식 이름을 표시하지 않는다.
- 기존 202개 기록, 세부 항목 883개는 42개 개발 단계(1.0~8.9)로 편집상 재분류한다. 원문, 개별 버전, 순서, 중복 구버전 식별자는 유지한다. 과거에 실제 베타·RC·정식 출시였다는 근거가 없는 항목에는 그 상태를 소급 부여하지 않는다.
- 첫 신규 목표는 9.0 Developer Beta 1. 내부 목표 9.0.0; PC/태블릿 사용자 지원 범위 축소와 모바일 중심 기능 전환을 Major로 묶었다.
- 배포 이후 검증된 운영 버전의 정본과 변경 이력을 공개 원장에 동기화한 뒤 다음 목표 버전을 등록한다. 실패한 빌드의 내부 번호를 운영 원장에 미리 쓰지 않는다.
